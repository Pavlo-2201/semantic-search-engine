# semantic-search-engine

Учебный проект: поиск по русскоязычной технической документации. На этом этапе
готовы корпус и лексический baseline (TF-IDF и BM25) с поиском из командной
строки; векторный поиск добавляется дальше.

## Задача

Построить поиск по русскоязычной технической документации: по запросу на
естественном языке находить страницы документации, которые на этот запрос
отвечают. Лексический baseline (TF-IDF/BM25) сравнивается с векторным поиском на
моделях sentence-transformers и индексом FAISS.

## Данные

Корпус — русские переводы MDN Web Docs из репозитория
[mdn/translated-content](https://github.com/mdn/translated-content).

- Текст статей MDN распространяется по лицензии
  [CC-BY-SA 2.5](https://creativecommons.org/licenses/by-sa/2.5/),
  авторы — MDN Web Docs contributors. Лицензия позволяет использовать и
  распространять текст при указании авторства, поэтому корпус подходит для
  учебного проекта.
- Страницы берутся через `raw.githubusercontent.com`: без токенов, без GitHub API.
- Список страниц — файл `files/ru/_wikihistory.json` в том же репозитории; его
  ключи это slug'и страниц русского перевода.
- Единица поиска — страница документации целиком.

Сам корпус в Git не добавляется (см. `.gitignore`), добавляется только скрипт
загрузки и метаданные запуска.

### Идентификаторы и версия данных

- `doc_id` считается от slug'а страницы: `mdnru-<первые 12 символов sha1(slug)>`.
  Он не зависит от порядка загрузки и от текста статьи, поэтому разметка запросов
  не ломается при повторной загрузке корпуса.
- Для каждого документа хранится `checksum` (sha256 текста), для корпуса целиком —
  `fingerprint_sha256` в файле `*.meta.json`. Ветка `main` репозитория MDN со
  временем меняется, и отпечаток позволяет проверить, что два запуска работали на
  одном и том же корпусе. Если нужна строгая воспроизводимость, в
  `configs/corpus.yaml` или в `--ref` указывается commit sha.

## Лексический baseline

Baseline — два способа ранжирования по совпадению слов:

- **TF-IDF** (`scikit-learn`): косинусная близость L2-нормированных TF-IDF
  векторов, `sublinear_tf=True`.
- **BM25 Okapi** (своя реализация, `k1=1.5`, `b=0.75`): в отличие от TF-IDF,
  насыщает вклад частоты термина и нормирует оценку на длину документа. В MDN
  длины страниц различаются в сотни раз, поэтому нормировка заметна.

Общий препроцессинг для обоих (`src/semsearch/text.py`): нижний регистр, склейка
«ё»/«е», токенизация по буквам и цифрам, короткий список русских стоп-слов и
стемминг Snowball только для слов с кириллицей — английские идентификаторы
(`querySelector`, `fetch`) стеммер портит без пользы. Стемминг нужен из-за
русской морфологии: «длина массива» и «массивы» без него не совпадут.
Заголовок страницы при индексации повторяется трижды: название страницы в
документации — самый точный её признак.

Оба поиска реализуют один интерфейс `Retriever` (`src/semsearch/retriever.py`):
`search(query, top_k) -> list[SearchHit]`. Векторный поиск будет реализовать его
же, поэтому CLI, оценка и следующий проект (RAG) не зависят от способа поиска.

## Установка

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
```

## Запуск

```bash
# полный корпус (около 2600 страниц)
python scripts/download_corpus.py --config configs/corpus.yaml --output data/corpus/mdn-ru.jsonl

# быстрая проверка на 20 страницах
python scripts/download_corpus.py --limit 20 --output data/corpus/sample.jsonl
```

Поиск:

```bash
python scripts/search.py --retriever bm25 --top-k 5 "как узнать длину массива в javascript"
python scripts/search.py --retriever tfidf --top-k 5 --json "центрировать блок по горизонтали css"
```

Тесты:

```bash
python -m pytest tests -q
```

## Результаты

Загрузка корпуса выполнена (`data/corpus/mdn-ru.meta.json`): 2635 страниц в
источнике, 2616 после отбора, 2570 документов в корпусе (3 страницы без файла в
репозитории, 43 короче 200 символов), 8 016 552 символа текста, медианная длина
страницы около 1300 символов.

Лексический поиск работает: индекс по 2570 документам строится примерно за 10
секунд на 4 ядрах CPU, один запрос BM25 выполняется за несколько миллисекунд.
Примеры ответов на шесть запросов — в [docs/examples-lexical.md](docs/examples-lexical.md).

Качество пока **не измерено**: набора запросов с разметкой релевантности ещё нет,
поэтому ни Recall@K, ни MRR@K не считались. По примерам видно обе типичные
проблемы лексического поиска: на запрос «что означает код ответа 404» первым
идёт нужная страница, а на «отправить http запрос из браузера» — страницы про
заголовок Expect и метод PUT, потому что слово «запрос» встречается в них часто,
а смысл запроса лексика не учитывает.

## Ограничения и следующие шаги

- Корпус привязан к ветке `main`: состав страниц может измениться, контроль —
  через отпечаток.
- Страницы индексируются целиком, без разбиения на фрагменты; для длинных статей
  это снижает точность и будет пересмотрено при переходе к векторному поиску.
- Качество лексического поиска не измерено: нет набора запросов с разметкой.
- Индекс строится при каждом запуске CLI заново, сохранения индекса пока нет.
- Дальше: embeddings и точный векторный поиск, FAISS, набор запросов и метрики.
