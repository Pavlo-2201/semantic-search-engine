# semantic-search-engine

Учебный проект: поиск по русскоязычной технической документации. На этом этапе
готовы корпус, лексический baseline (TF-IDF и BM25), точный векторный поиск,
индекс FAISS с сохранением и загрузкой, набор запросов с разметкой и метрики
Recall@K, MRR@K, nDCG@K.

## Задача

Построить поиск по русскоязычной технической документации: по запросу на
естественном языке находить страницы документации, которые на этот запрос
отвечают. Лексический baseline (TF-IDF/BM25) сравнивается с векторным поиском на
моделях sentence-transformers и индексом FAISS.

## Данные

Корпус — русские переводы MDN Web Docs из репозитория
[mdn/translated-content](https://github.com/mdn/translated-content).

- Текст статей MDN распространяется по лицензии
  [CC-BY-SA 2.5](https://creativecommons.org/licenses/by-sa/2.5/),
  авторы — MDN Web Docs contributors. Лицензия позволяет использовать и
  распространять текст при указании авторства, поэтому корпус подходит для
  учебного проекта.
- Страницы берутся через `raw.githubusercontent.com`: без токенов, без GitHub API.
- Список страниц — файл `files/ru/_wikihistory.json` в том же репозитории; его
  ключи это slug'и страниц русского перевода.
- Единица поиска — страница документации целиком.

Сам корпус в Git не добавляется (см. `.gitignore`), добавляется только скрипт
загрузки и метаданные запуска.

### Идентификаторы и версия данных

- `doc_id` считается от slug'а страницы: `mdnru-<первые 12 символов sha1(slug)>`.
  Он не зависит от порядка загрузки и от текста статьи, поэтому разметка запросов
  не ломается при повторной загрузке корпуса.
- Для каждого документа хранится `checksum` (sha256 текста), для корпуса целиком —
  `fingerprint_sha256` в файле `*.meta.json`. Ветка `main` репозитория MDN со
  временем меняется, и отпечаток позволяет проверить, что два запуска работали на
  одном и том же корпусе. Если нужна строгая воспроизводимость, в
  `configs/corpus.yaml` или в `--ref` указывается commit sha.

## Лексический baseline

Baseline — два способа ранжирования по совпадению слов:

- **TF-IDF** (`scikit-learn`): косинусная близость L2-нормированных TF-IDF
  векторов, `sublinear_tf=True`.
- **BM25 Okapi** (своя реализация, `k1=1.5`, `b=0.75`): в отличие от TF-IDF,
  насыщает вклад частоты термина и нормирует оценку на длину документа. В MDN
  длины страниц различаются в сотни раз, поэтому нормировка заметна.

Общий препроцессинг для обоих (`src/semsearch/text.py`): нижний регистр, склейка
«ё»/«е», токенизация по буквам и цифрам, короткий список русских стоп-слов и
стемминг Snowball только для слов с кириллицей — английские идентификаторы
(`querySelector`, `fetch`) стеммер портит без пользы. Стемминг нужен из-за
русской морфологии: «длина массива» и «массивы» без него не совпадут.
Заголовок страницы при индексации повторяется трижды: название страницы в
документации — самый точный её признак.

Оба поиска реализуют один интерфейс `Retriever` (`src/semsearch/retriever.py`):
`search(query, top_k) -> list[SearchHit]`. Векторный поиск будет реализовать его
же, поэтому CLI, оценка и следующий проект (RAG) не зависят от способа поиска.

## Векторный поиск

Поиск начинается с **точного** перебора (`src/semsearch/dense.py`): векторы
L2-нормированы, поэтому скалярное произведение равно косинусной близости. Точный
поиск даёт верхнюю границу качества для модели, и относительно него дальше
измеряется потеря от приближённого индекса.

Кодировщики описаны в `configs/models.yaml`, и требования модели задаются явно, а
не угадываются (`src/semsearch/embedding.py`):

- префиксы запроса и документа (у E5 это `query: ` и `passage: `) приписываются
  раздельно: `encode_queries` и `encode_documents` — разные методы;
- способ пулинга читается из загруженной модели и сверяется с конфигурацией;
  расхождение это ошибка конфигурации, а не молчаливое поведение;
- нормализация обязательна для косинуса и для FAISS с внутренним произведением;
- документ кодируется как «заголовок. начало текста» (по умолчанию 2000 символов):
  трансформеры всё равно обрезают вход, а начало статьи MDN описывает её суть.

Доступны два бэкенда:

| бэкенд | модель | когда нужен |
|---|---|---|
| `sentence-transformers` | `e5-small`, `e5-base`, `labse`, `rubert-tiny2` | основной вариант, нужны веса с Hugging Face |
| `lsa` | `lsa-300` | TF-IDF и усечённое SVD, обучается на корпусе; работает без загрузки весов и служит нижней границей качества векторного поиска |
| `word2vec` | `word2vec-200` | Word2Vec (skip-gram) на корпусе, вектор текста — среднее по словам с весом IDF; вторая обучаемая модель, устроенная иначе, чем LSA |

### Индекс FAISS

`src/semsearch/faiss_index.py` собирает индекс, сохраняет его и загружает обратно.

- Соответствие **позиция в индексе -> doc_id** хранится рядом с индексом в
  `meta.json`: FAISS знает только позиции 0..N-1, и без явного соответствия индекс,
  собранный на другом порядке документов, молча вернул бы не те страницы. Поиск
  возвращает doc_id, а не позиции.
- Вместе с индексом сохраняются конфигурация модели и отпечаток корпуса. При
  загрузке состав документов и отпечаток сверяются с корпусом; расхождение это
  ошибка, а не предупреждение.
- Модель `lsa-300` обучается на корпусе, поэтому сохраняется в тот же каталог
  (`encoder.pkl`): иначе запрос кодировался бы другой моделью, чем документы.
- Типы индекса: `flat-ip` (точный, внутреннее произведение по нормированным
  векторам), `ivf-flat` и `hnsw` (приближённые). Проверено тестом, что точный
  индекс FAISS даёт тот же результат, что и полный перебор на numpy.

### Ограничение окружения

В окружении, где собирался проект, нет доступа к huggingface.co, поэтому веса
предобученных моделей скачать не удалось. Весь путь (кодирование, индекс,
метрики, latency) измерен на `lsa-300`; строки для `e5-*` и `labse` помечены
«не измерено», команды полного запуска приведены. Механика работы с
sentence-transformers (префиксы, пулинг, нормализация) проверена тестами на
крошечной локальной модели со случайными весами — см. `tests/conftest.py`.

## Оценка качества

Разметка: `data/queries/dev.jsonl` (36 запросов для настройки) и
`data/queries/test.jsonl` (36 запросов для финальной проверки). Наборы не
пересекаются ни по идентификаторам, ни по тексту запросов.

Запросы и разметку я написал вручную по страницам корпуса: формулировал запрос
так, как его задал бы человек, и отмечал страницы, которые на него отвечают
(градация 2 — прямо отвечает, 1 — отвечает частично). Разметка ссылается на
страницы по slug, `doc_id` вычисляется из него той же функцией, что при сборке
корпуса.

Метрики: Recall@K, MRR@K, nDCG@K с градуированной релевантностью. Полные
определения, происхождение разметки и её ограничения — в
[docs/evaluation.md](docs/evaluation.md). Коротко: **72 запроса от одного
аннотатора — это набор для разработки, а не промышленный benchmark**; разметка
неполная (на запрос часто отвечает и неотмеченная страница), поэтому абсолютные
значения занижены, и корректно сравнивать только модели между собой на одной
разметке.

## Установка

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
```

## Запуск

```bash
# полный корпус (около 2600 страниц)
python scripts/download_corpus.py --config configs/corpus.yaml --output data/corpus/mdn-ru.jsonl

# быстрая проверка на 20 страницах
python scripts/download_corpus.py --limit 20 --output data/corpus/sample.jsonl
```

Поиск:

```bash
python scripts/search.py --retriever bm25 --top-k 5 "как узнать длину массива в javascript"
python scripts/search.py --retriever tfidf --top-k 5 --json "центрировать блок по горизонтали css"
python scripts/search.py --retriever dense --model lsa-300 --top-k 5 "как узнать длину массива"

# тот же запрос предобученной моделью (нужен доступ к huggingface.co)
python scripts/search.py --retriever dense --model e5-small --top-k 5 "как узнать длину массива"
```

Сборка индекса и поиск по сохранённому индексу:

```bash
python scripts/build_index.py --model lsa-300 --output data/indexes/lsa-300-flat
python scripts/build_index.py --model lsa-300 --index-type hnsw --output data/indexes/lsa-300-hnsw
python scripts/search.py --retriever faiss --index data/indexes/lsa-300-flat --top-k 5 "длина массива"
```

Оценка качества:

```bash
python scripts/evaluate.py --retriever bm25 --queries data/queries/dev.jsonl --output results
python scripts/evaluate.py --retriever dense --model lsa-300 --queries data/queries/dev.jsonl --output results
python scripts/evaluate.py --retriever faiss --index data/indexes/lsa-300-hnsw --queries data/queries/dev.jsonl
```

Сравнение всех способов поиска на одном корпусе и одних запросах:

```bash
python scripts/compare_models.py --config configs/compare.yaml --output results/comparison
```

Чтобы добавить в сравнение предобученные модели, нужен доступ к huggingface.co;
после этого в `configs/compare.yaml` у прогонов `e5-small` и `labse` ставится
`enabled: true` и запускается та же команда.

Тесты:

```bash
python -m pytest tests -q
```

## Результаты

Загрузка корпуса выполнена (`data/corpus/mdn-ru.meta.json`): 2635 страниц в
источнике, 2616 после отбора, 2570 документов в корпусе (3 страницы без файла в
репозитории, 43 короче 200 символов), 8 016 552 символа текста, медианная длина
страницы около 1300 символов.

Лексический поиск работает: индекс по 2570 документам строится примерно за 10
секунд на 4 ядрах CPU, один запрос BM25 выполняется за несколько миллисекунд.
Примеры ответов на шесть запросов — в [docs/examples-lexical.md](docs/examples-lexical.md).

Точный векторный поиск на `lsa-300` тоже работает: кодирование 2570 документов
занимает около 11 секунд на 4 ядрах CPU, поиск по 300-мерным векторам полным
перебором — около 15 мс на запрос. Сравнение ответов BM25 и `lsa-300` на одних
запросах — в [docs/examples-dense.md](docs/examples-dense.md).

### Сравнение способов поиска

Все строки получены на одном корпусе (2570 документов) и одних запросах;
полная таблица и машиночитаемый вид — в
[results/comparison/comparison.md](results/comparison/comparison.md) и
`results/comparison/comparison.json`.

Финальный набор (`test.jsonl`, 36 запросов, не использовался при настройке):

| поиск | Recall@1 | Recall@5 | Recall@10 | MRR@10 | nDCG@10 |
|---|---|---|---|---|---|
| BM25 | 0.083 | 0.375 | 0.500 | 0.268 | 0.315 |
| TF-IDF | 0.097 | 0.278 | 0.458 | 0.209 | 0.258 |
| dense exact, `lsa-300` | 0.097 | 0.375 | **0.569** | 0.255 | **0.322** |
| dense exact, `word2vec-200` | 0.069 | **0.403** | 0.528 | 0.265 | 0.307 |
| FAISS hnsw, `lsa-300` | 0.097 | 0.375 | 0.569 | 0.255 | 0.322 |
| FAISS ivf-flat, `lsa-300` | 0.097 | 0.361 | 0.556 | 0.247 | 0.314 |
| dense, `e5-small` | не измерено | не измерено | не измерено | не измерено | не измерено |
| dense, `labse` | не измерено | не измерено | не измерено | не измерено | не измерено |

Что видно:

- обе векторные модели достают больше нужного в top-10, чем лексический поиск
  (0.569 и 0.528 против 0.500 у BM25), но по первой позиции разницы практически
  нет: все способы на этом наборе часто ставят на первое место соседнюю страницу
  документации;
- BM25 заметно лучше TF-IDF — нормировка на длину документа на корпусе, где
  страницы различаются по длине в сотни раз, работает;
- разница между `lsa-300` и `word2vec-200` в пределах нескольких процентных
  пунктов, а набор маленький, поэтому «одна модель лучше другой» по этим числам
  утверждать нельзя;
- предобученные модели (`e5-small`, `labse`) в этом окружении недоступны, их
  строки — «не измерено»; команда полного запуска ниже.

### Потеря качества приближённого индекса

Измерена относительно точного поиска по тем же векторам `lsa-300`
(`loss_vs_exact` в `results/comparison/comparison.json`):

| индекс | ΔRecall@10 (dev) | ΔRecall@10 (test) | ΔnDCG@10 (test) |
|---|---|---|---|
| hnsw (M=32, efSearch=64) | 0.000 | 0.000 | 0.000 |
| ivf-flat (nlist=64, nprobe=8) | −0.074 | −0.014 | −0.008 |

На корпусе из 2570 векторов HNSW с такими параметрами не теряет ничего, а
ivf-flat теряет заметно: при `nprobe=8` часть кластеров не просматривается.
Выводы верны для этого размера корпуса; на миллионах векторов картина другая.

Индекс FAISS на 2570 векторах (300 измерений) собирается за те же ~10 секунд,
что и кодирование, а загружается с диска за 0.13 секунды — поиск по сохранённому
индексу не требует пересчёта корпуса.

Качество пока **не измерено**: набора запросов с разметкой релевантности ещё нет,
поэтому ни Recall@K, ни MRR@K не считались. По примерам видно обе типичные
проблемы лексического поиска: на запрос «что означает код ответа 404» первым
идёт нужная страница, а на «отправить http запрос из браузера» — страницы про
заголовок Expect и метод PUT, потому что слово «запрос» встречается в них часто,
а смысл запроса лексика не учитывает.

## Ограничения и следующие шаги

- Корпус привязан к ветке `main`: состав страниц может измениться, контроль —
  через отпечаток.
- Страницы индексируются целиком, без разбиения на фрагменты; для длинных статей
  это снижает точность и будет пересмотрено при переходе к векторному поиску.
- Качество не измерено ни для лексического, ни для векторного поиска: нет набора
  запросов с разметкой релевантности.
- Предобученные модели в этом окружении недоступны (см. выше), поэтому измерена
  только локально обучаемая `lsa-300`.
- Разметка небольшая и неполная, от одного аннотатора: см. ограничения в
  [docs/evaluation.md](docs/evaluation.md).
- Предобученные модели не измерены: нет доступа к huggingface.co.
- Абсолютные значения метрик низкие в основном из-за неполноты разметки: в корпусе
  десятки близких страниц (например, методы `Array`), и поиск часто выдаёт
  полезную, но не отмеченную страницу.
- Дальше: измерение latency (кодирование запроса и поиск отдельно, p50/p95) и
  разбор провальных запросов.
