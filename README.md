# semantic-search-engine

Поиск по русскоязычной технической документации: лексический baseline (TF-IDF и
BM25), векторный поиск на embeddings и индекс FAISS, с измеренным качеством и
задержками.

## Задача

По запросу на естественном языке («как узнать длину массива», «что означает код
ответа 404») находить страницы технической документации, которые на этот запрос
отвечают. Лексический поиск сравнивается с векторным на одном корпусе и одних
запросах; качество измеряется метриками Recall@K, MRR@K и nDCG@K на отдельных
наборах для настройки и для финальной проверки.

## Данные

Корпус — русские переводы MDN Web Docs из репозитория
[mdn/translated-content](https://github.com/mdn/translated-content).

- **Лицензия**: текст статей MDN доступен по
  [CC-BY-SA 2.5](https://creativecommons.org/licenses/by-sa/2.5/), авторство —
  MDN Web Docs contributors. Лицензия разрешает использование и распространение
  при указании авторства, поэтому корпус подходит для учебного проекта.
- **Получение**: `raw.githubusercontent.com`, без токенов и GitHub API. Список
  страниц — `files/ru/_wikihistory.json`, сами статьи —
  `files/ru/<slug в нижнем регистре>/index.md`.
- **Версия данных**: по умолчанию ветка `main`; для строгой воспроизводимости
  в `configs/corpus.yaml` или в `--ref` указывается commit sha. Вместе с корпусом
  пишется `data/corpus/mdn-ru.meta.json` с датой загрузки и отпечатком.
- **Объём**: 2635 страниц в источнике, 2616 после отбора, **2570 документов** в
  корпусе (3 страницы отсутствуют в репозитории, 43 короче 200 символов),
  8 016 552 символа, медианная длина страницы ≈ 1300 символов, максимальная
  ≈ 74 000.
- **Что в Git не попадает**: корпус, индексы, веса и кеши (см. `.gitignore`).
  В Git есть скрипт загрузки, метаданные, разметка запросов и результаты
  измерений.

### Идентификаторы

`doc_id = mdnru-<первые 12 символов sha1(slug)>`. Он не зависит ни от порядка
загрузки, ни от текста статьи, поэтому разметка запросов не ломается при
повторной загрузке корпуса. Для каждого документа хранится sha256 текста, для
корпуса целиком — `fingerprint_sha256`: по нему видно, что два эксперимента шли на
одном и том же корпусе.

## Установка

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
```

`torch`, `transformers` и `sentence-transformers` нужны только для предобученных
моделей; лексический поиск, `lsa-300` и `word2vec-200` работают без них.

## Команды

```bash
# корпус (около 2600 страниц, несколько минут)
python scripts/download_corpus.py --config configs/corpus.yaml --output data/corpus/mdn-ru.jsonl

# поиск
python scripts/search.py --retriever bm25 --top-k 5 "как узнать длину массива в javascript"
python scripts/search.py --retriever dense --model lsa-300 --top-k 5 "центрировать блок по горизонтали"
python scripts/search.py --retriever faiss --index data/indexes/lsa-300-flat --json "код ответа 404"

# индекс FAISS: сборка и сохранение
python scripts/build_index.py --model lsa-300 --index-type flat-ip --output data/indexes/lsa-300-flat
python scripts/build_index.py --model lsa-300 --index-type hnsw   --output data/indexes/lsa-300-hnsw

# метрики
python scripts/evaluate.py --retriever bm25 --queries data/queries/dev.jsonl --output results
python scripts/evaluate.py --retriever dense --model lsa-300 --queries data/queries/test.jsonl --output results

# сравнение всех способов на одном корпусе и одних запросах
python scripts/compare_models.py --config configs/compare.yaml --output results/comparison

# задержки и разбор провальных запросов
python scripts/benchmark_latency.py --repeats 200 --output results/latency.json
python scripts/analyze_failures.py --output results/failures.json --markdown results/failures.md

# тесты
python -m pytest
```

Всё сразу, в том же порядке, в котором получены числа в этом README:

```bash
bash scripts/run_all.sh
```

Полный прогон предобученной модели (нужен доступ к huggingface.co):

```bash
python scripts/build_index.py --model e5-small --index-type flat-ip --output data/indexes/e5-small-flat
python scripts/evaluate.py --retriever faiss --index data/indexes/e5-small-flat \
    --queries data/queries/test.jsonl --output results
# и в configs/compare.yaml поставить enabled: true у прогонов e5-small и labse
python scripts/compare_models.py --config configs/compare.yaml --output results/comparison
```

## Как это устроено

| модуль | что делает |
|---|---|
| `semsearch/corpus.py` | документ, устойчивые ID, чтение и запись JSONL, отпечаток корпуса |
| `semsearch/mdn.py` | загрузка страниц MDN, Markdown → текст |
| `semsearch/text.py` | нормализация русского текста, стемминг Snowball |
| `semsearch/lexical.py` | TF-IDF (scikit-learn) и BM25 Okapi (своя реализация) |
| `semsearch/embedding.py` | кодировщики: sentence-transformers, LSA, Word2Vec |
| `semsearch/dense.py` | точный векторный поиск и поиск по индексу FAISS |
| `semsearch/faiss_index.py` | сборка, сохранение, загрузка индекса, соответствие ID |
| `semsearch/evaluation.py` | разметка запросов и метрики |
| `semsearch/latency.py` | измерение задержек, описание оборудования |
| `semsearch/pipeline.py` | сборка поиска по имени для CLI и экспериментов |
| `semsearch/retriever.py` | общий контракт поиска (`search`, `search_batch`) |

Все способы поиска реализуют один контракт `Retriever`, поэтому CLI, оценка,
сравнение и следующий проект не зависят от того, лексический поиск внутри или
векторный. Описание контракта и примеры подключения —
[docs/retriever-api.md](docs/retriever-api.md).

### Требования моделей заданы явно

Кодировщики описаны в `configs/models.yaml`; код не угадывает их требования:

- префиксы запроса и документа приписываются раздельно (`encode_queries` и
  `encode_documents` — разные методы; у E5 это `query: ` и `passage: `);
- способ пулинга читается из загруженной модели и сверяется с конфигурацией,
  расхождение — ошибка, а не молчаливое поведение;
- нормализация включается флагом и обязательна для косинуса и для FAISS с
  внутренним произведением;
- документ кодируется как «заголовок. начало текста» (2000 символов по
  умолчанию): трансформеры всё равно обрезают вход, а начало статьи MDN описывает
  её суть.

Доступные модели:

| модель | бэкенд | когда нужна |
|---|---|---|
| `lsa-300` | TF-IDF + усечённое SVD, обучается на корпусе | работает без загрузки весов |
| `word2vec-200` | Word2Vec skip-gram на корпусе, вектор текста — среднее с весом IDF | вторая векторная модель, устроенная иначе |
| `rubert-tiny2` | `sentence-transformers`, предобученная (312 измерений, ревизия `e8ed3b0c`) | измерена: веса скачаны заранее и положены в `models/rubert-tiny2` |
| `e5-small`, `e5-base` | `sentence-transformers`, multilingual-e5 | основной вариант, нужны веса с Hugging Face |
| `labse` | `sentence-transformers` | альтернатива для сравнения |

Если доступа к huggingface.co нет, веса можно скачать отдельно и указать каталог
в `local_path` модели (`configs/models.yaml`). Тогда модель грузится с диска
(`local_files_only=True`), а сравнение не падает у того, кто склонировал
репозиторий без весов: такой прогон пропускается с пометкой «не измерено».
Ревизия модели (`revision`) фиксирует веса так же, как commit sha фиксирует
данные.

### Индекс FAISS

FAISS знает только позиции векторов, поэтому соответствие **позиция → doc_id**
хранится рядом с индексом в `meta.json`, и поиск возвращает `doc_id`. Там же
лежат конфигурация модели и отпечаток корпуса; при загрузке состав документов и
отпечаток сверяются с корпусом. Обученная на корпусе модель сохраняется в тот же
каталог (`encoder.pkl`), иначе запрос кодировался бы не той моделью, что
документы. Типы: `flat-ip` (точный), `ivf-flat` и `hnsw` (приближённые); тестом
проверено, что точный индекс FAISS совпадает с полным перебором на numpy.

## Результаты

### Качество

Все строки получены на одном корпусе (2570 документов) и одних запросах;
машинная форма — `results/comparison/comparison.json`, таблицы —
[results/comparison/comparison.md](results/comparison/comparison.md).

**dev (36 запросов, на них настраивались параметры)**

| поиск | Recall@1 | Recall@5 | Recall@10 | MRR@10 | nDCG@10 |
|---|---|---|---|---|---|
| BM25 | **0.125** | 0.232 | 0.361 | 0.211 | 0.238 |
| TF-IDF | 0.093 | 0.232 | 0.287 | 0.201 | 0.204 |
| `lsa-300`, точный поиск | 0.093 | 0.245 | **0.505** | **0.219** | **0.287** |
| `word2vec-200`, точный поиск | 0.079 | **0.250** | 0.389 | 0.209 | 0.239 |
| `lsa-300`, FAISS hnsw | 0.093 | 0.245 | 0.505 | 0.219 | 0.287 |
| `lsa-300`, FAISS ivf-flat | 0.065 | 0.236 | 0.431 | 0.210 | 0.253 |
| `rubert-tiny2`, точный поиск | 0.069 | 0.162 | 0.227 | 0.156 | 0.164 |
| `e5-small`, `labse` | не измерено | не измерено | не измерено | не измерено | не измерено |

**test (36 запросов, при настройке не использовались)**

| поиск | Recall@1 | Recall@5 | Recall@10 | MRR@10 | nDCG@10 |
|---|---|---|---|---|---|
| BM25 | 0.083 | 0.375 | 0.500 | **0.268** | 0.315 |
| TF-IDF | 0.097 | 0.278 | 0.458 | 0.209 | 0.258 |
| `lsa-300`, точный поиск | **0.097** | 0.375 | **0.569** | 0.255 | **0.322** |
| `word2vec-200`, точный поиск | 0.069 | **0.403** | 0.528 | 0.265 | 0.307 |
| `lsa-300`, FAISS hnsw | 0.097 | 0.375 | 0.569 | 0.255 | 0.322 |
| `lsa-300`, FAISS ivf-flat | 0.097 | 0.361 | 0.556 | 0.247 | 0.314 |
| `rubert-tiny2`, точный поиск | 0.083 | 0.222 | 0.292 | 0.195 | 0.191 |
| `e5-small`, `labse` | не измерено | не измерено | не измерено | не измерено | не измерено |

Выводы, которые эти числа выдерживают:

- векторный поиск достаёт больше нужного в top-10, чем лексический (0.569 и
  0.528 против 0.500 у BM25), но по первой позиции разницы нет: на этом наборе
  все способы часто ставят первой соседнюю страницу документации;
- BM25 заметно лучше TF-IDF — нормировка на длину документа на корпусе, где
  страницы различаются в сотни раз, работает;
- разница между `lsa-300` и `word2vec-200` в пределах нескольких процентных
  пунктов; на 36 запросах это не основание утверждать, что одна модель лучше;
- **предобученная `rubert-tiny2` оказалась худшей из всех** (Recall@10 0.292
  против 0.500 у BM25), и разрыв здесь уже большой, не в пределах шума. Это
  ожидаемо: rubert-tiny2 обучена оценивать сходство коротких предложений, а не
  искать документ по запросу, у неё 312 измерений и три слоя, и документ из двух
  тысяч символов она сжимает в вектор, в котором тематические различия почти
  пропадают (косинусы между неродственными страницами — 0.62–0.63). Вывод: «взять
  любую предобученную модель» не работает, нужна модель, обученная под retrieval
  (к ним относятся multilingual-e5 с префиксами `query:`/`passage:` и LaBSE).

### Потеря качества приближённого индекса

Измерена относительно точного поиска по тем же векторам `lsa-300`
(`loss_vs_exact` в `results/comparison/comparison.json`):

| индекс | ΔRecall@10 (dev) | ΔRecall@10 (test) | ΔnDCG@10 (test) |
|---|---|---|---|
| hnsw (M=32, efSearch=64) | 0.000 | 0.000 | 0.000 |
| ivf-flat (nlist=64, nprobe=8) | −0.074 | −0.014 | −0.008 |

На 2570 векторах HNSW с такими параметрами не теряет ничего, ivf-flat теряет
заметно: при `nprobe=8` часть кластеров не просматривается. Для корпусов на
порядки больше картина другая.

### Задержки

Кодирование запроса и поиск по индексу измерены отдельно, с прогревом (20
вызовов) и 200 замерами, прогон повторён дважды. Оборудование: 4 ядра Intel Xeon
2.10GHz, 15.7 ГБ памяти, без GPU. Методика и полная таблица —
[docs/latency.md](docs/latency.md).

| поиск | кодирование p50/p95, мс | поиск по индексу p50/p95, мс | итого p50/p95, мс |
|---|---|---|---|
| BM25 | — | — | 1.1 / 1.6 |
| TF-IDF | — | — | 1.6 / 2.0 |
| `lsa-300`, точный поиск | 6.3 / 7.4 | 0.35 / 1.19 | 6.7 / 8.6 |
| `lsa-300`, FAISS hnsw | 10.0 / 13.5 | 0.10 / 0.16 | 10.1 / 13.7 |
| `lsa-300`, FAISS ivf-flat | 10.8 / 12.9 | 0.02 / 0.04 | 10.8 / 13.0 |
| `word2vec-200`, точный поиск | 0.09 / 0.13 | 0.53 / 1.02 | 0.62 / 1.16 |
| `rubert-tiny2`, точный поиск | 3.9 / 4.6 | 0.36 / 0.65 | 4.2 / 5.2 |
| `e5-small`, `labse` | не измерено | не измерено | не измерено |

Числа первого прогона; второй прогон и разброс между ними — в
[docs/latency.md](docs/latency.md).

Главное: время уходит на кодирование запроса, а не на поиск — у `lsa-300`
разница в десятки и сотни раз. Поэтому приближённый индекс на таком корпусе
выигрыша не даёт: экономия в десятые доли миллисекунды не видна на фоне
кодирования, а ivf-flat при этом теряет качество. Кодирование `lsa-300` одной и
той же моделью в разных строках и прогонах дало от 5.3 до 11.4 мс: это шум
виртуальной машины, абсолютные значения стоит читать с точностью «единицы
миллисекунд». Маленькая `rubert-tiny2` (3 слоя) кодирует запрос стабильно за
3.7–3.9 мс — быстрее, чем `lsa-300` через scikit-learn.

### Провальные запросы

Полный разбор с примерами — [docs/failures.md](docs/failures.md). Четыре
причины, видимые в данных:

1. **Запрос по-русски, страница названа английским идентификатором**
   («подписаться на нажатие кнопки» → `addEventListener`). Лексический поиск
   бессилен по построению, а модели, обученные на этом же корпусе, такие пары
   связать не могут. Предобученная `rubert-tiny2`, худшая в среднем, часть таких
   запросов вытягивает единственная («чтобы сайт работал без интернета» →
   Service Worker на первом месте) — это довод за многоязычную модель, обученную
   под retrieval, и за гибридный поиск: способы ошибаются на разных запросах.
2. **Общие слова притягивают короткие страницы глоссария** («чтобы сайт работал
   без интернета» → «Интернет-провайдер»).
3. **Соседние страницы раздела неотличимы** при индексации страницы целиком
   («запретить всплытие события» → `Event: свойство target`).
4. **Неполнота разметки**: часть «провалов» — это отвечающие страницы, которых
   нет в разметке.

### Разметка запросов

`data/queries/dev.jsonl` (36 запросов для настройки) и
`data/queries/test.jsonl` (36 для финальной проверки); наборы не пересекаются ни
по идентификаторам, ни по тексту запросов — это проверяется тестом. Разметку я
написал вручную по страницам корпуса: градация 2 — страница прямо отвечает на
запрос, 1 — отвечает частично. Определения метрик, происхождение разметки и её
ограничения — [docs/evaluation.md](docs/evaluation.md).

**Это не промышленный benchmark.** 72 запроса от одного аннотатора — набор для
разработки. Разметка неполная: в корпусе десятки близких страниц, и поиск часто
выдаёт полезную, но не отмеченную страницу. Поэтому абсолютные значения метрик
занижены, и корректно сравнивать только способы поиска между собой на одной
разметке.

## Что проверяется тестами

`python -m pytest` — 69 тестов, все проходят. Существенное:

- устойчивость `doc_id` к порядку загрузки и к правкам текста;
- отсутствие пересечений между наборами для настройки и для теста;
- определения метрик на синтетических выдачах (идеальный порядок даёт nDCG = 1,
  вклад вне top-K равен нулю, градации влияют на nDCG);
- точный индекс FAISS совпадает с полным перебором на numpy;
- сохранение и загрузка индекса дают тот же результат; изменение корпуса при
  загрузке обнаруживается;
- механика sentence-transformers (префиксы доходят до модели, нормализация
  включается и выключается, несовпадение пулинга даёт ошибку) — на крошечной
  локальной модели со случайными весами, без загрузки весов из сети; пулинг в
  конфигурации `rubert-tiny2` сверяется с `1_Pooling/config.json` самой модели;
- воспроизводимость обучаемых моделей (`lsa`, `word2vec`) и совпадение векторов
  после сохранения и загрузки;
- прогрев не попадает в статистику задержек, процентиль считается по
  зафиксированному определению.

## Ограничения

- **Модели, обученные под retrieval, не измерены.** В окружении, где собирался
  проект, нет доступа к huggingface.co. Из предобученных измерена только
  `rubert-tiny2`, веса которой были скачаны заранее; `multilingual-e5` и LaBSE —
  «не измерено», команды полного запуска приведены выше.
- **Единица поиска — страница целиком.** Для длинных страниц это снижает точность:
  отличительный абзац усредняется с остальным текстом.
- **Разметка небольшая и неполная**, от одного аннотатора.
- **Задержки измерены на виртуальной машине**; разброс между прогонами — единицы
  миллисекунд.
- **Корпус привязан к ветке `main`** репозитория MDN: состав страниц со временем
  меняется, контроль — через отпечаток.
- Блоки кода при сборке корпуса выброшены; для запросов, где ответ именно в коде,
  это потеря.

## Следующие шаги

1. Прогнать `multilingual-e5` и LaBSE (нужен доступ к huggingface.co или
   заранее скачанные веса в `local_path`): по разбору провалов это самое крупное
   ожидаемое улучшение.
2. Разбить страницы на фрагменты (заголовок раздела плюс абзац) и искать по
   фрагментам — и для точности, и для будущего RAG.
3. Пополнить разметку: отмечать все отвечающие страницы, а не только самую
   очевидную; тогда абсолютные значения метрик станут осмысленными.
4. Отдельный вес или фильтр для коротких страниц глоссария.
5. Переранжирование top-50 вторым способом (cross-encoder или гибрид BM25 и
   векторного поиска): лексический и векторный поиск проваливают разные запросы,
   значит их объединение должно давать выигрыш.
6. Qdrant как альтернатива FAISS: базовая версия закончена, и теперь понятно, что
   сравнивать нужно не только задержку поиска, но и время кодирования запроса.

## Этапы и принятые решения

| этап | дата | решение и почему |
|---|---|---|
| Корпус | 2026-05-25 | MDN на русском через `raw.githubusercontent.com`: разрешённая лицензия, нет токенов и API. `doc_id` от slug'а, чтобы разметка не ломалась при повторной загрузке; отпечаток корпуса, потому что источник меняется. Блоки кода выброшены: англоязычные идентификаторы для поиска по смыслу — шум |
| Лексический baseline | 2026-06-01 | TF-IDF и BM25 на общем препроцессинге, чтобы разница относилась к ранжированию. Стемминг Snowball только для кириллицы: английские идентификаторы он портит. Заголовок повторяется трижды — это самый точный признак страницы |
| Embeddings | 2026-06-08 | Начато с точного перебора: это верхняя граница качества модели. Требования модели (префиксы, пулинг, нормализация) заданы конфигурацией и проверяются по загруженной модели. Бэкенд `lsa` добавлен, потому что веса с Hugging Face недоступны, а измерять нужно на чём-то реальном |
| FAISS | 2026-06-15 | Соответствие позиция → `doc_id` и отпечаток корпуса хранятся рядом с индексом: иначе индекс на другом корпусе молча вернёт не те страницы. Обучаемая модель сохраняется вместе с индексом |
| Разметка и метрики | 2026-06-22 | Два непересекающихся набора: настройка и финальная проверка. Градуированная релевантность, потому что nDCG без неё теряет смысл. Ограничения разметки описаны прямо, чтобы числа не читались как benchmark |
| Сравнение | 2026-06-26 | Добавлена вторая обучаемая модель (Word2Vec), устроенная иначе, чем LSA, — иначе сравнивать нечего. Все прогоны на одном корпусе и одних запросах, кодирование кэшируется. Потеря приближённых индексов измерена относительно точного поиска |
| Задержки и провалы | 2026-06-29 | Кодирование и поиск измерены отдельно: это показало, что узкое место — кодирование, а не индекс. Прогон повторён дважды, чтобы разброс был виден. Провалы разобраны по причинам, а не только посчитаны |
| Итог | 2026-07-03 | Публичный интерфейс (`open_retriever`, `Retriever`, `SearchHit`) и `scripts/run_all.sh`, воспроизводящий все числа README. Добавлена загрузка весов из локального каталога с фиксированной ревизией — так измерена предобученная `rubert-tiny2`; проверка пулинга поймала ошибку в её конфигурации (там CLS, а не среднее). Корпус и контракт поиска подготовлены для следующего проекта с RAG |
