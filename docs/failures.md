# Провальные запросы: что именно ломается

Провал — размеченная страница не попала в первые 10 результатов. Сгенерированные
таблицы и полные списки запросов: [results/failures.md](../results/failures.md),
машиночитаемый вид — `results/failures.json`. Команда:

```bash
python scripts/analyze_failures.py --output results/failures.json --markdown results/failures.md
```

|---|---|---|---|---|
| dev (36) | BM25 | 5 | 16 | 20 |

нашёл только лексический поиск, мало (1 и 2), а только векторный — заметно
больше (8 и 5): векторный поиск вытягивает часть запросов, сформулированных не
словами документации, но своих провалов у него не меньше.

## Разбор причин

Ниже — причины, которые видны в данных. Каждая иллюстрируется запросом из
`results/failures.md`.

### 1. Запрос по-русски, а страница называется по-английски

«подписаться на нажатие кнопки» → ожидалась `EventTarget/addEventListener`, все
четыре способа выдали `MouseEvent.button`. «добавить класс элементу из кода» →
ожидался `Element/classList`, выдано «Селекторы по классу». «плавное изменение
цвета при наведении мыши» → ожидался `transition`, выдано «Псевдоклассы».

Название нужной страницы — английский идентификатор, а в русском тексте статьи
он встречается в примерах кода, которые при сборке корпуса выброшены. Лексический
поиск тут бессилен по построению. Обученные на корпусе `lsa-300` и
`word2vec-200` тоже не помогают: чтобы связать «подписаться на нажатие» с
`addEventListener`, нужна модель, которая видела такие пары, а не 2570 страниц
этого же корпуса. Это главный довод за предобученную многоязычную модель
(`multilingual-e5`, LaBSE) — именно такие запросы она должна вытягивать.

### 2. Общие слова запроса притягивают страницы глоссария

«ошибка при обращении к другому домену из браузера» → ожидался `CORS`, TF-IDF
выдал «Доменное имя». «чтобы сайт работал без интернета» → ожидался Service
Worker, выдано «Интернет-провайдер». «узнать где находится пользователь» → выдан
«Прокси сервер».

Страницы глоссария короткие и состоят почти целиком из общеупотребительных слов,
поэтому нормировка BM25 на длину документа играет против нас: короткая страница с
одним совпадением получает высокую оценку. Возможные направления: отдельный вес
для раздела `Glossary`, или отсечение по длине, или переранжирование top-50
вторым способом. В этой версии ничего из этого не сделано.

### 3. Соседние страницы одного раздела неотличимы

«запретить всплытие события к родителю» → ожидался `Event/stopPropagation`, все
способы выдали `Event: свойство target`. «проверить есть ли значение в массиве» →
ожидался `Array/includes`, выдано `in`, «Массив», `TypedArray.prototype.set()`.

В корпусе десятки страниц про массивы и события с почти одинаковой русской
прозой («Метод … возвращает …»), различающиеся одним-двумя терминами. Поиск по
странице целиком усредняет эти различия. Направление: индексировать не страницу,
а фрагменты (заголовок раздела плюс абзац) — тогда отличительный абзац не тонет в
остальном тексте. Это же нужно будет для RAG-проекта.

### 4. Неполная и спорная разметка

«дождаться выполнения нескольких асинхронных операций сразу» → ожидались
`Promise/all` и `Promise/allSettled`, векторный поиск первым дал «Использование
промисов». Эта страница на запрос, по сути, отвечает, но в разметке её нет, и
запрос считается проваленным.

Такие случаи завышают число провалов: часть «провалов» — это пропуски в разметке,
а не ошибки поиска. Поэтому абсолютные значения метрик занижены, и сравнивать
корректно только способы между собой на одной разметке (см.
[docs/evaluation.md](evaluation.md)).

Отдельно: «плавная покадровая анимация в браузере» — плохо сформулированный мной
запрос. Ожидался `requestAnimationFrame`, но запрос одинаково хорошо описывает и
CSS-анимацию, которую поиск и выдал. Это ошибка составителя запроса, а не поиска.

## Что из этого следует для следующей версии

1. Предобученная многоязычная модель — самое крупное ожидаемое улучшение
   (причина 1, самая частая).
2. Разбиение страниц на фрагменты (причина 3) — и для поиска, и для RAG.
3. Разметку нужно пополнить: отмечать все отвечающие страницы, а не только
   самую очевидную (причина 4).
4. Отдельный вес или фильтр для коротких страниц глоссария (причина 2).
