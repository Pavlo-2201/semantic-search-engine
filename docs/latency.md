# Задержки поиска

Все числа получены реальными прогонами `scripts/benchmark_latency.py`; машинная
форма — `results/latency.json` и `results/latency-run2.json` (два независимых
прогона).

## Как измерялось

- **Кодирование запроса и поиск по индексу измерены отдельно**: это разные
  операции, и оптимизируются они по-разному. Для лексического поиска разделение
  не имеет смысла (разбор запроса на термины неотделим от обхода словаря),
  поэтому для BM25 и TF-IDF приведён один общий этап.
- **Прогрев**: 20 вызовов до измерения, их результат не учитывается. Первый вызов
  включает ленивую инициализацию (загрузка стеммера, первый проход BLAS) и
  медленнее остальных в разы.
- **Повторные измерения**: 200 замеров на этап, запросы перебираются по кругу
  (36 запросов из `dev.jsonl`), по одному запросу за раз — так, как работает
  поиск в ответ на запрос пользователя, а не батчами.
- **Процентили**: метод ближайшего ранга, значение с номером `ceil(P/100 · N)`
  по отсортированным замерам.
- Весь прогон повторён дважды, чтобы видеть разброс между прогонами.

## Что из этого видно

1. **Время тратится на кодирование запроса, а не на поиск.** У `lsa-300`
   кодирование занимает 5–11 мс, а поиск по индексу — 0.02–0.38 мс, то есть в
   десятки и сотни раз меньше. Оптимизировать индекс при таком соотношении
   бессмысленно: выигрыш съест кодирование. Для `lsa-300` кодирование — это
   TF-IDF-преобразование плюс умножение на матрицу SVD, и на одном коротком
   запросе накладные расходы scikit-learn заметнее самой арифметики.
2. **Предобученная `rubert-tiny2` кодирует запрос быстрее, чем `lsa-300`**: 3.7–3.9
   мс и стабильно в обоих прогонах. У неё три слоя и 312 измерений, а запрос
   короткий; это не общее свойство трансформеров — у `multilingual-e5-small` 12
   слоёв, и кодирование будет заметно дольше (не измерено).
3. **Приближённый индекс действительно быстрее точного перебора**: 0.02 мс
   (ivf-flat) и 0.08–0.10 мс (hnsw) против 0.35–0.38 мс. Но на 2570 векторах это
   десятые доли миллисекунды, которые не видны на фоне кодирования; при этом
   ivf-flat теряет в качестве (см. README). На таком корпусе приближённый индекс
   не нужен — он имеет смысл от сотен тысяч векторов.
4. **Лексический поиск на этом корпусе по задержке сопоставим с векторным**:
   1.1 мс у BM25 против 0.6–11 мс у векторных вариантов.
5. **Разброс между прогонами существенный.** Кодирование `lsa-300` в двух
   прогонах дало 6.3 и 11.4 мс при точном переборе и 10.0 и 5.5 мс в строке с
   hnsw — это одна и та же модель и один и тот же код, то есть шум виртуальной
   машины. Поэтому сравнивать этапы между собой корректно внутри одного прогона,
   а абсолютные значения стоит читать с точностью «единицы миллисекунд». Для
   надёжных чисел нужно выделенное железо и больше повторов.
6. `word2vec-200` кодирует запрос за 0.09 мс — это несколько обращений к таблице
   векторов и усреднение, без матричных умножений.

Модели `multilingual-e5` и LaBSE не измерены: в окружении нет доступа к
huggingface.co, а их веса заранее не скачивались.

## Команда

```bash
python scripts/benchmark_latency.py --repeats 200 --warmup 20 --output results/latency.json
```
