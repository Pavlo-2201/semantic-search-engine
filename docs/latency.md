# Задержки поиска

Все числа получены реальными прогонами `scripts/benchmark_latency.py`; машинная
форма — `results/latency.json` и `results/latency-run2.json` (два независимых
прогона).

## Как измерялось

- **Кодирование запроса и поиск по индексу измерены отдельно**: это разные
  операции, и оптимизируются они по-разному. Для лексического поиска разделение
  не имеет смысла (разбор запроса на термины неотделим от обхода словаря),
  поэтому для BM25 и TF-IDF приведён один общий этап.
- **Прогрев**: 20 вызовов до измерения, их результат не учитывается. Первый вызов
  включает ленивую инициализацию (загрузка стеммера, первый проход BLAS) и
  медленнее остальных в разы.
- **Повторные измерения**: 200 замеров на этап, запросы перебираются по кругу
  (36 запросов из `dev.jsonl`), по одному запросу за раз — так, как работает
  поиск в ответ на запрос пользователя, а не батчами.
- **Процентили**: метод ближайшего ранга, значение с номером `ceil(P/100 · N)`
  по отсортированным замерам.
- Весь прогон повторён дважды, чтобы видеть разброс между прогонами.

## Что из этого видно

1. **Время тратится на кодирование запроса, а не на поиск.** У `lsa-300`
   кодирование занимает 8–13 мс, а поиск по индексу — 0.03–0.44 мс, то есть в
   20–400 раз меньше. Оптимизировать индекс при таком соотношении бессмысленно:
   выигрыш съест кодирование. Для `lsa-300` кодирование это TF-IDF-преобразование
   плюс умножение на матрицу SVD, и на одном коротком запросе накладные расходы
   scikit-learn заметнее самой арифметики.
2. **Приближённый индекс действительно быстрее точного перебора**: 0.03 мс
   (ivf-flat) и 0.09 мс (hnsw) против 0.44 мс. Но на 2570 векторах это
   десятые доли миллисекунды, которые не видны на фоне кодирования; при этом
   ivf-flat теряет в качестве (см. README). На таком корпусе приближённый индекс
   не нужен — он имеет смысл от сотен тысяч векторов.
3. **Лексический поиск на этом корпусе по задержке сопоставим с векторным**:
   1.1 мс у BM25 против 0.6–13 мс у векторных вариантов.
4. **Разброс между прогонами существенный.** Кодирование `lsa-300` дало 6.0 и
   13.3 мс в двух прогонах с одной и той же моделью: это шум виртуальной машины,
   а не разница в коде. Поэтому сравнивать этапы между собой корректно внутри
   одного прогона, а абсолютные значения стоит читать с точностью «единицы
   миллисекунд». Для надёжных чисел нужно выделенное железо и больше повторов.
5. `word2vec-200` кодирует запрос за 0.11 мс — это несколько обращений к таблице
   векторов и усреднение, без матричных умножений.

Предобученные модели не измерены: в окружении нет доступа к huggingface.co.
Порядок ожидаемых величин для них другой — прямой проход трансформера на CPU
занимает десятки миллисекунд на запрос, то есть кодирование станет ещё более
доминирующим этапом.

## Команда

```bash
python scripts/benchmark_latency.py --repeats 200 --warmup 20 --output results/latency.json
```
