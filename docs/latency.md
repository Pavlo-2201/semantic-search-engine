# Задержки поиска

Все числа получены реальными прогонами `scripts/benchmark_latency.py`; машинная
форма — `results/latency.json` и `results/latency-run2.json` (два независимых
прогона).

## Как измерялось

- **Кодирование запроса и поиск по индексу измерены отдельно**: это разные
  операции, и оптимизируются они по-разному. Для лексического поиска разделение
  не имеет смысла (разбор запроса на термины неотделим от обхода словаря),
  поэтому для BM25 и TF-IDF приведён один общий этап.
- **Прогрев**: 20 вызовов до измерения, их результат не учитывается. Первый вызов
  включает ленивую инициализацию (загрузка стеммера, первый проход BLAS) и
  медленнее остальных в разы.
- **Повторные измерения**: 200 замеров на этап, запросы перебираются по кругу
  (36 запросов из `dev.jsonl`), по одному запросу за раз — так, как работает
  поиск в ответ на запрос пользователя, а не батчами.
- **Процентили**: метод ближайшего ранга, значение с номером `ceil(P/100 · N)`
  по отсортированным замерам.
- Весь прогон повторён дважды, чтобы видеть разброс между прогонами.

## Что из этого видно

1. **Время тратится на кодирование запроса, а не на поиск.** У `lsa-300`
   кодирование занимает 4–13 мс, а поиск по индексу — 0.03–0.41 мс, то есть в
   десятки и сотни раз меньше; у `e5-small` 13 мс против 0.5 мс. Оптимизировать
   индекс при таком соотношении бессмысленно: выигрыш съест кодирование. Для
   `lsa-300` кодирование — это TF-IDF-преобразование плюс умножение на матрицу
   SVD, и на одном коротком запросе накладные расходы scikit-learn заметнее самой
   арифметики.
2. **Предобученные модели кодируют стабильно, и цена качества видна.**
   `rubert-tiny2` (3 слоя, 312 измерений) — 3.4–3.6 мс, `e5-small` (12 слоёв,
   384 измерения) — 13.0–13.4 мс, в обоих прогонах почти одинаково. `e5-small`
   примерно вчетверо медленнее `rubert-tiny2` и на порядок медленнее BM25, но
   это всё ещё миллисекунды на запрос, а по качеству она лучшая из измеренных
   (см. README). На CPU это приемлемая цена.
3. **Приближённый индекс действительно быстрее точного перебора**: 0.03 мс
   (ivf-flat) и 0.10 мс (hnsw) против 0.40–0.41 мс. Но на 2570 векторах это
   десятые доли миллисекунды, которые не видны на фоне кодирования; при этом
   ivf-flat теряет в качестве (см. README). На таком корпусе приближённый индекс
   не нужен — он имеет смысл от сотен тысяч векторов.
4. **Лексический поиск на этом корпусе по задержке сопоставим с векторным**:
   1.1 мс у BM25 против 0.5–14 мс у векторных вариантов.
5. **Разброс между прогонами и строками существенный.** Кодирование `lsa-300`
   дало 10.0 и 12.8 мс в строке точного перебора и 4.8 и 3.9 мс в строке с hnsw —
   это одна и та же модель и один и тот же код, то есть шум виртуальной машины
   (в более раннем прогоне соотношение было обратным). Поэтому абсолютные значения
   стоит читать с точностью «единицы миллисекунд», а для надёжных чисел нужно
   выделенное железо и больше повторов. Устойчиво воспроизводится только порядок
   величин: поиск — доли миллисекунды, кодирование — миллисекунды.
6. `word2vec-200` кодирует запрос за 0.08–0.09 мс — это несколько обращений к
   таблице векторов и усреднение, без матричных умножений.

`e5-small` измерена по заранее скачанным весам (ревизия `614241f`). LaBSE не
измерена: в окружении нет доступа к huggingface.co, а её веса заранее не
скачивались.

## Команда

```bash
python scripts/benchmark_latency.py --repeats 200 --warmup 20 --output results/latency.json
```
