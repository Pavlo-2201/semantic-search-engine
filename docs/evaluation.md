# Набор запросов и метрики

## Что это за набор

Два файла разметки:

- `data/queries/dev.jsonl` — 36 запросов для настройки: на них выбираются
  параметры (препроцессинг, представление документа, параметры индекса);
- `data/queries/test.jsonl` — 36 запросов для финальной проверки; они не
  использовались при выборе параметров.

Наборы не пересекаются ни по `query_id`, ни по тексту запроса — это проверяется
тестом. Разделение нужно, чтобы итоговые числа не были числами, по которым
подбирались настройки.

## Откуда взялись запросы и разметка

Запросы и разметку я написал вручную: открывал страницы русского MDN из корпуса,
формулировал запрос так, как его задал бы человек («сколько элементов в массиве»,
а не «Array.prototype.length»), и отмечал страницы, которые на этот запрос
отвечают. Для разметки использовались заголовок и начало статьи.

Градации релевантности:

- `2` — страница прямо отвечает на запрос;
- `1` — страница по теме и полезна, но отвечает частично;
- неразмеченные страницы считаются нерелевантными (`0`).

Разметка ссылается на страницы по `slug`, а `doc_id` вычисляется из него той же
функцией, что и при сборке корпуса, поэтому разметка и корпус не могут
разойтись незаметно. При загрузке проверяется, что все размеченные страницы в
корпусе есть.

### Это не промышленный benchmark

72 запроса, размеченные одним человеком по заголовкам и началу статей, — это
набор для разработки, а не benchmark. Его ограничения:

- **Одна разметка, один аннотатор.** Согласованность между аннотаторами не
  измерялась, поэтому часть границ «отвечает / не отвечает» спорная.
- **Разметка неполная.** В корпусе много близких страниц (например, десятки
  методов `Array`), и на запрос нередко отвечает не только отмеченная страница.
  Поэтому абсолютные значения метрик занижены: поиск может выдать на первом
  месте полезную страницу, которая в разметке отсутствует, и получить ноль.
  Сравнивать между собой модели на одной и той же разметке корректно, объявлять
  полученные числа «качеством поиска по документации» — нет.
- **Небольшой размер.** На 36 запросах разница в несколько процентных пунктов
  между моделями статистически не значима; уверенно читаются только крупные
  различия.

## Определения метрик

K — глубина, на которой считается метрика. Все метрики усредняются по запросам
(macro-average).

**Recall@K** — доля релевантных страниц запроса, попавших в первые K
результатов:

```
Recall@K = |relevant ∩ top-K| / |relevant|
```

Отвечает на вопрос «сколько нужного поиск вообще достаёт».

**MRR@K** (Mean Reciprocal Rank) — средний обратный ранг первой релевантной
страницы:

```
MRR@K = mean(1 / rank_первой_релевантной), 0 если в top-K релевантных нет
```

Отвечает на вопрос «насколько высоко стоит первый полезный ответ».

**nDCG@K** — нормированный дисконтированный накопленный выигрыш с учётом
градаций:

```
DCG@K  = Σ_{i=1..K} (2^grade_i − 1) / log2(i + 1)
IDCG@K = DCG@K идеального порядка размеченных страниц
nDCG@K = DCG@K / IDCG@K
```

Учитывает и позицию, и степень релевантности: страница с оценкой 2 на первом
месте даёт больше, чем страница с оценкой 1.

Реализация — `src/semsearch/evaluation.py`, проверки определений —
`tests/test_evaluation.py`.

## Как запускать

```bash
python scripts/evaluate.py --retriever bm25  --queries data/queries/dev.jsonl --output results
python scripts/evaluate.py --retriever tfidf --queries data/queries/dev.jsonl --output results
python scripts/evaluate.py --retriever dense --model lsa-300 --queries data/queries/dev.jsonl --output results
```

Для каждого прогона записываются два файла: `<label>__<queries>.json` с
усреднёнными метриками, параметрами и отпечатком корпуса и
`<label>__<queries>.per_query.jsonl` с результатом по каждому запросу (для
разбора провальных запросов).
